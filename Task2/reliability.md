# Паттерны надёжности



## 1. Circuit Breaker



Для вызовов зависимых сервисов (PostgreSQL, Redis) используется паттерн Circuit Breaker. Он предотвращает каскадные отказы и позволяет системе плавно деградировать.



**Реализация:**

- Внедряется на уровне клиента (например, в gRPC-клиенте).

- Настраиваются пороги:

- **Порог ошибок:** 50% неудачных запросов за последние 10 секунд (например).

- **Таймаут ожидания перехода в полуоткрытое состояние:** 30 секунд.

- **Количество запросов в полуоткрытом состоянии:** 5 (для проверки восстановления).

- При размыкании цепь перехватывает вызовы и сразу возвращает fallback-ответ (например, «no bid» или кэшированная ставка) без попытки обращения к зависимому сервису.



**Применение:**

- Для вызовов PostgreSQL (если кэш недоступен).

- Для вызовов Redis (если Redis недоступен, Circuit Breaker переключает на прямой запрос к БД, но если и БД недоступна - fallback).



## 2. Повторные попытки с экспоненциальной задержкой (Retry with Exponential Backoff)



Для временных сбоев (сетевые флаттеры, кратковременная недоступность) применяются повторные попытки с увеличивающейся задержкой.



**Параметры:**

- Максимальное количество попыток - 3.

- Начальная задержка - 100 мс.

- Множитель - 2 (100, 200, 400 мс).

- Добавляется случайный джиттер.



**Применение:**

- При вызовах к PostgreSQL (если запрос завершился ошибкой из-за таймаута или блокировки).

- При вызовах к Redis (если операция не удалась из-за сетевой проблемы).

- При публикации событий в Kafka (если брокер временно недоступен).



Важно: повторные попытки **не применяются** к запросам, которые уже заведомо обречены на ошибку (например, аутентификация, некорректные данные). Используется фильтрация исключений.



## 3. Идемпотентность финансовых операций



Финансовые операции (списание средств за выигранный аукцион, пополнение баланса) должны быть идемпотентными, чтобы избежать двойного списания при повторной отправке события.



**Реализация:**

- Каждое событие аукциона содержит уникальный идентификатор `auction_id` (генерируется Сервером ставок).

- Финансовый сервис хранит таблицу `processed_auctions` с полями `auction_id` и `status` (processed/pending).

- При получении события `AuctionWon` сервис проверяет, обрабатывалось ли это событие ранее.

- Если событие уже обработано - игнорирует его (возвращает успех без изменения баланса).

- Если не обработано - выполняет списание и записывает факт обработки.

- Все операции списания выполняются в рамках транзакции (обновление баланса + запись в `processed_auctions`).



**Дополнительно:**

- Для пополнения баланса (внешний платёжный шлюз) используется аналогичный механизм с `payment_id`.

- Kafka гарантирует at-least-once доставку, поэтому возможны дублирующиеся сообщения - идемпотентность обязательна.



## 4. Резервные стратегии (Fallback)



Если критический компонент (БД или кэш) недоступен, система должна продолжать работать, хотя бы с ограниченной функциональностью, чтобы не терять аукционы полностью.



**Варианты fallback-стратегий:**



- **Кэшированные ставки:** Если Redis недоступен, но есть локальный кэш (например, в памяти сервиса) с предыдущими данными, использовать его. Можно хранить последние загруженные кампании с TTL (например, 1 минута).

- **Дефолтные ставки:** Если нет данных о конкретном объявлении или кампании, использовать базовую ставку из запроса или минимальную ставку (например, 0.01), чтобы не пропускать аукцион.

- **«No bid»:** Если невозможно получить данные для расчёта (и кэш, и БД недоступны) - вернуть пустой ответ, чтобы не рисковать неправильной ставкой, которая может превысить бюджет.



**Приоритет fallback-цепочки:**

1. Попытка получить данные из Redis.

2. При ошибке - попытка получить из PostgreSQL.

3. При ошибке - использование дефолтных значений (base_bid из запроса).

4. Крайний случай - возврат «no bid».



Все fallback-решения логируются для последующего анализа и корректировки.



## 5. Мониторинг и алертинг



Для всех паттернов надёжности настроены метрики:

- Количество срабатываний Circuit Breaker (открыто/закрыто).

- Количество повторных попыток и их успешность.

- Частота использования fallback-стратегий.

- Время ответа каждого компонента.



Алерты настроены на:

- Превышение порога ошибок (>5% за 1 минуту).

- Частое открытие Circuit Breaker (>3 раз за 5 минут).

- Падение доступности Redis или PostgreSQL.



Все метрики экспортируются в Prometheus и визуализируются в Grafana.
