# Схема взаимодействия и выбор протоколов



## Внешнее взаимодействие с DSP

Протокол интеграции - **OpenRTB** (версия 2.5) по HTTPS. DSP присылает bid request в формате JSON, AdScale отвечает bid response. Это стандарт для RTB, поддерживается всеми DSP.



## Внутреннее взаимодействие



### Между Рекламным сервером и Сервером ставок

Выбран **gRPC** (синхронный вызов) по следующим причинам:

- **Низкая задержка** - gRPC работает поверх HTTP/2, бинарный протокол (Protobuf) быстрее JSON.

- **Строгая типизация** - контракт чётко определён, меньше ошибок.

- **Поддержка потоков** - не требуется сейчас, но может пригодиться для batch-запросов.

- **Интеграция с существующим стеком** - есть клиенты для C++, Go, Python.



REST был бы медленнее (текстовый формат, накладные расходы на HTTP/1.1) и менее строгий. Асинхронный подход не подходит, потому что ответ нужен немедленно (SLA 100 мс).



### Между Сервером ставок и БД / кэшем

- К Redis - синхронно через Redis Protocol (высокая производительность).

- К PostgreSQL - синхронно через JDBC (но только при отсутствиях в кэше, чтобы минимизировать).



### Потоковая обработка событий

Используется **Kafka** для:

- **Публикации результатов аукционов** - Сервер ставок отправляет событие `AuctionWon` в топик `auction-results`. Это событие потом потребляется Финансовым сервисом для списания средств и Сервисом аналитики для построения отчётов.

- **Событий показов/кликов** - Сервис выдачи отправляет события в топик `user-events`, откуда их читает Сервис статистики.



**Почему Kafka:**

- Высокая пропускная способность (миллионы событий/сек).

- Гарантия доставки (at-least-once).

- Возможность репликации и сохранения истории.

- Отвязывает критическое действие (аукцион) от тяжёлой записи в БД.



## API Gateway

Для интеграции с DSP необходим **API Gateway**, так как:

- Он будет принимать все внешние HTTP-запросы (включая bid requests) и маршрутизировать их в Рекламный сервер (или напрямую в Сервер ставок, если архитектура позволит).

- Обеспечивает единую точку входа для аутентификации, rate limiting, Circuit Breaker, сбора метрик.

- В текущем случае проектируется отдельный шлюз для DSP-трафика (может быть общим с Advertiser Dashboard).



Выбор технологии - **Envoy**. Envoy легковесен, имеет отличную поддержку gRPC, метрики, Circuit Breaker. Учитывая высокие требования к latency, предпочтение отдается Envoy, настроенному на низкую задержку.
