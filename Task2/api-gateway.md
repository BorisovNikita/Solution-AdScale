# Проект API Gateway для DSP-интеграции



## Роль API Gateway

- Принимает HTTP-запросы от DSP-партнёра (OpenRTB).

- Проверяет аутентификацию (API-ключ или JWT).

- Применяет rate limiting для защиты от DDoS и перегрузок.

- Проксирует запрос в Рекламный сервер (или напрямую в Сервер ставок) с добавлением заголовков.

- Собирает метрики времени ответа, кодов ошибок.

- Реализует паттерн Circuit Breaker для вызовов внутренних сервисов.



## Маршрутизация

- `POST /rtb/bid` -> Рекламный сервер (или Bidding Service). На первом этапе можно маршрутизировать прямо в Bidding Service, если Рекламный сервер ещё не выделен.

- `GET /health` - для проверки жизнеспособности шлюза.



## Аутентификация

Используется API-ключ, передаваемый в заголовке `X-API-Key`. Шлюз проверяет ключ по белым спискам (хранятся в конфиге или в Redis). Для дополнительной безопасности можно внедрить mTLS.



## Rate Limiting

Настраивается лимит на количество запросов в секунду для каждого API-ключа (например, 1000 RPS). Реализуется через Envoy's.



## Circuit Breaker

Для вызовов внутреннего сервиса (Рекламный сервер / Bidding Service) используется Circuit Breaker:

- При достижении порога ошибок (50% за 10 сек) - размыкается, и шлюз возвращает fallback-ответ (например, HTTP 503).

- Через таймаут (30 сек) переходит в полуоткрытое состояние, пробует один запрос.

- Реализуется через Envoy's.



## Мониторинг времени отклика

- Метрики: P50, P95, P99 latency для каждого DSP-партнёра.

- Счётчики успешных/ошибочных запросов.

- Интеграция с Prometheus + Grafana.

- Alert's при превышении порога (например, P95 > 80 мс).



## Fallback стратегия

Если внутренний сервис недоступен, шлюз может вернуть пустой ответ (no bid) или кэшированную ставку (если есть запасной вариант). Это позволяет не терять аукционы полностью, хотя и снижает доходность.
