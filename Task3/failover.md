# Отказоустойчивость данных и 12-факторные приложения

## 1. RPO и RTO для каждого сервиса

| Сервис | RPO (допустимая потеря данных) | RTO (время восстановления) | Описание |
|--------|--------------------------------|----------------------------|-------------|
| **Сервис ставок** (PostgreSQL) | 5 минут | 15 минут | Данные аукционов критичны для финансов, но потеря за 5 минут допустима (прибыль может быть упущена, но не катастрофична). Восстановление из реплики + WAL за 15 минут. |
| **Сервис кампаний** (PostgreSQL) | 1 минута | 10 минут | Изменения кампаний (бюджеты, статусы) должны быть минимально потеряны, т.к. влияют на текущие ставки. Репликация с синхронной записью на мастер. |
| **Сервис статистики** (ClickHouse) | 1 час | 1 час | События показов/кликов могут быть потеряны за час – не критично для бизнеса, т.к. отчётность может быть восстановлена из архивов или повторно загружена из Kafka. |
| **Сервис аналитики** (ClickHouse) | 1 час | 2 часа | Аналитические данные менее критичны; могут быть перестроены из сырых событий из Kafka или бэкапов. |
| **Финансовый сервис** (PostgreSQL) | 0 / 1 минута | 5 минут | Финансовые транзакции не должны теряться. Используется синхронная репликация и WAL-архивация с минимальной задержкой. Восстановление из реплики + WAL за 5 минут. |

## 2. Стратегия резервного копирования

| Сервис | Периодичность | Хранение |
|--------|---------------|----------|
| **Сервис ставок** (PostgreSQL) | Ежедневный полный бэкап + непрерывная архивация WAL |  30 дней |
| **Сервис кампаний** (PostgreSQL) | Ежедневный полный бэкап + непрерывная архивация WAL | 30 дней |
| **Сервис статистики** (ClickHouse) | Ежедневный бэкап (снэпшот партиций) | 7 дней |
| **Сервис аналитики** (ClickHouse) | Ежедневный бэкап (снэпшот партиций) + репликация | 7 дней |
| **Финансовый сервис** (PostgreSQL) | Ежедневный полный бэкап + непрерывная WAL + синхронная репликация | 30 дней |

## 3. Соответствие принципам 12-факторных приложений

Ниже приведён анализ текущего состояния и целевые улучшения по каждому фактору для AdScale.

### Кодовая база (Codebase)
- **Текущее состояние:** Код разбит на несколько репозиториев (C++, Go, Python, Node.js части). Это усложняет управление версиями и развёртывание.
- **Целевое состояние:** Все микросервисы хранятся в одном монорепозитории (или в одном репозитории с модульной структурой). Используется единая система контроля версий (Git). Одна кодовая база для всех окружений.

### Зависимости (Dependencies)
- **Текущее состояние:** Зависимости указаны в различных файлах (requirements.txt, go.mod, package.json, CMakeLists.txt). Но могут быть неполные или неявные зависимости (например, системные библиотеки).
- **Целевое состояние:** Все зависимости явно декларированы и изолированы (использование Docker-контейнеров с фиксированными версиями). Сборка воспроизводима. Зависимости устанавливаются автоматически при сборке контейнера.

### Конфигурация (Config)
- **Текущее состояние:** Конфигурация хранится в коде (файлы .env, config.yml) и в переменных окружения частично.
- **Целевое состояние:** Вся конфигурация вынесена в переменные окружения. Параметры не зашиты в код. Используется один механизм для всех микросервисов.

### Сторонние службы (Backing Services)
- **Текущее состояние:** Жёсткая привязка к PostgreSQL, Redis, Kafka. Замена сервиса потребует изменения кода.
- **Целевое состояние:** Все бэкенд-сервисы рассматриваются как прикреплённые ресурсы. Используются абстракции (интерфейсы) и конфигурация URL через переменные окружения.

### Сборка, выпуск, запуск (Build, Release, Run)
- **Текущее состояние:** Процессы не разделены, деплой выполняется вручную.
- **Целевое состояние:** Автоматизированный CI/CD pipeline:
  - **Build:** Сборка Docker-образов.
  - **Release:** Добавление конфигурации и создание релиза.
  - **Run:** Запуск контейнеров в кластере Kubernetes.

### Процессы (Processes)
- **Текущее состояние:** Некоторые сервисы сохраняют состояние (например, локальный кэш).
- **Целевое состояние:** Все микросервисы являются stateless. Данные хранятся во внешних хранилищах (БД, Redis, Kafka). Любой экземпляр сервиса может быть перезапущен без потери данных, масштабирование по горизонтали.

### Порт привязки (Port Binding)
- **Текущее состояние:** Используется внешний веб-сервер (Nginx) для проксирования, но приложения сами слушают порты.
- **Целевое состояние:** Каждый микросервис экспортирует свой HTTP/gRPC-сервис через привязку к порту (например, 8080). API Gateway (Envoy) маршрутизирует трафик. Приложение самодостаточно, не требует внешнего веб-сервера.

### Конкурентные процессы (Concurrency)
- **Текущее состояние:** Ограниченная поддержка многопоточности, масштабирование вручную.
- **Целевое состояние:** Используется горизонтальное масштабирование через Kubernetes HPA (Horizontal Pod Autoscaler) на основе RPS/CPU.

### Утилизируемость (Disposability)
- **Текущее состояние:** Время старта и остановки велико, что затрудняет быстрое масштабирование.
- **Целевое состояние:** Микросервисы быстро стартуют и корректно завершаются, обрабатывая сигналы SIGTERM.

### Среды разработки и эксплуатации (Dev/Prod Parity)
- **Текущее состояние:** Различия в окружениях (ОС, версии, конфигурации) приводят к багам.
- **Целевое состояние:** Использование Docker и Kubernetes как локально, так и в production. Одинаковые образы и конфигурации, различаются только переменные окружения.

### Логи (Logs)
- **Текущее состояние:** Логи пишутся в файлы, что усложняет их агрегацию.
- **Целевое состояние:** Все логи выводятся в stdout/stderr.

### Административные процессы (Admin Processes)
- **Текущее состояние:** Миграции БД, очистка кэша, пересчёт статистики выполняются вручную или через скрипты, не всегда в той же среде.
- **Целевое состояние:** Административные задачи (миграции схемы БД, бэкапы, пересчёт агрегатов) запускаются как одноразовые контейнеры в том же окружении, используя те же переменные окружения и доступ к ресурсам.

---

Текущая архитектура AdScale не соответствует 12 факторам, но целевое состояние (через 1 год) будет им соответствовать за счёт внедрения контейнеризации, CI/CD, stateless-сервисов, выноса конфигурации, централизованного логирования и административных задач через оркестратор.
