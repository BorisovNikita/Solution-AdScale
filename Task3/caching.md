# Стратегия кэширования

## 1. Что кэшировать

| Тип данных | Источник | Ключ | TTL | Причина |
|------------|----------|------|-----|---------|
| **Кампании** | PostgreSQL (Сервис ставок) | `campaign:{id}` | 5 минут | Часто читаются в каждом аукционе. |
| **Объявления (Ads)** | PostgreSQL (Сервис ставок) | `ad:{id}` | 5 минут | Критичны для расчёта ставок. |
| **Модификаторы ставок** | PostgreSQL (Сервис ставок) | `bid_modifiers:{ad_id}` | 5 минут | Используются для расчёта финальной ставки. |
| **Бюджеты (дневные)** | PostgreSQL (Сервис ставок) | `budget_daily:{campaign_id}:{date}` | 1 минута | Изменяются часто (списания), требуется актуальность. |
| **Результаты аукционов** | Не кэшируются | - | - | Записываются в БД и отправляются в Kafka. |

## 2. Где разместить Redis

- **Один общий кластер Redis** для всех сервисов (с изоляцией по ключам или использованием разных баз данных).
- Размещается в том же Kubernetes-кластере, что и сервисы, для минимизации сетевой задержки.

**Альтернатива:** Отдельные Redis для Сервиса ставок (для данных аукциона) и для Сервиса кампаний (для кэширования CRUD-данных). На первом этапе достаточно общего кластера.

## 3. TTL и стратегия инвалидации

**TTL (время жизни):**
- `campaign`, `ad`, `bid_modifiers` - 5 минут.
- `budget_daily` - 1 минута.

**Стратегия инвалидации:**
1. При чтении: сначала запрос в Redis, при промахе - в PostgreSQL, результат сохраняется в Redis с TTL.
2. При обновлении данных (через Рекламный кабинет или Сервис кампаний):
   - Обновление в PostgreSQL.
   - Публикация события `CampaignUpdated` в Kafka.
   - Потребитель (Сервис ставок) удаляет соответствующий ключ из Redis (инвалидация) или обновляет его.

**Notice:** Для бюджетов используется более частый TTL (1 минута), чтобы избежать превышения дневного лимита из-за кэширования.

## 4. Прогрев кэша

**Стратегия:**
- При старте Сервиса ставок или при расширении кластера выполняется прогрев кэша:
  - Загружаются все активные кампании (`status = 'active'`).
  - Загружаются все активные объявления.
  - Загружаются модификаторы для этих объявлений.
  - Загружаются текущие дневные бюджеты.
- Прогрев выполняется пачками (batch) с ограничением скорости, чтобы не перегружать PostgreSQL.
- Можно использовать фоновый процесс, который периодически обновляет кэш для наиболее активных кампаний.

**При обновлении данных:** Используется паттерн «инвалидация при обновлении».
