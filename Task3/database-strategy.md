# Стратегия данных для каждого сервиса



| Сервис | Тип базы данных | Обоснование |
|--------|-----------------|-------------|
| **Сервис ставок** (Bidding Service) | PostgreSQL (основная, OLTP) | Требуется строгая консистентность для данных аукциона (ставки, кампании, модификаторы). Используются сложные транзакционные запросы с JOIN. Поддержка ACID критична для корректного расчёта ставок и записи истории. Возможно партиционирование `AuctionLog` по времени. |
| **Сервис кампаний** (Campaign Service) | PostgreSQL (основная, OLTP) | Хранит рекламные кампании, объявления, таргетинговые правила. Требует ACID для CRUD-операций (создание, редактирование, изменение статусов и бюджетов). Часто используется для чтения в Сервисе ставок (через кэш), поэтому важна производительность чтения. |
| **Сервис статистики** (Statistics Service) | ClickHouse (OLAP) | Колоночная СУБД, оптимизированная для аналитических запросов и высокой скорости вставки (миллионы событий/сек). Поддерживает партиционирование по времени, сжатие и материализованные представления. Не требует ACID, допускает согласованность в конечном счете. |
| **Сервис аналитики** (Analytics Service) | ClickHouse (та же инстанция или отдельная read-replica) | Выполняет тяжёлые аналитические запросы (отчёты по кампаниям, агрегации за длительные периоды). ClickHouse обеспечивает высокую скорость таких запросов. Использует те же данные, что и Сервис статистики, но для изоляции нагрузки может быть выделена отдельная реплика. |
| **Финансовый сервис** (Financial Service) | PostgreSQL (OLTP, шардированная) | Требуется строгая консистентность и ACID для финансовых транзакций (списания, пополнения балансов, выставление счетов). Поддержка транзакций критична для предотвращения ошибок списания. Шардирование по `advertiser_id` для горизонтального масштабирования. |
