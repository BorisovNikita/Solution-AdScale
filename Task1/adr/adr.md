# ADR-001: Стратегия эволюции архитектуры

**Дата:** 2026-09-08
**Статус:** Accepted

## Контекст

AdScale - SaaS-платформа для размещения цифровой рекламы, работающая на рынке несколько лет. Система представляет собой гибридный монолит с единой PostgreSQL, развёрнутый вручную в одном production-кластере. Текущая пиковая нагрузка - 15 000 RPS, P95 latency составляет 110–120 мс при допустимом пороге < 100 мс. Компания получила предложение об интеграции с крупной DSP-площадкой, что добавит 20% трафика (до 18 000 RPS) в ближайшие 3 месяца, а через год ожидается рост до 50 000 RPS. Новый партнёр требует строгих SLA: стабильное время ответа не более 80 мс (с возможным буфером до 100 мс) и штрафы за деградацию.

Ключевые архитектурные драйверы:
- **Производительность:** P95 latency < 100 мс для аукциона.
- **Масштабируемость:** поддержка 18 000 RPS через 3 месяца и 50 000 RPS через год.
- **Доступность:** SLA 99,9% в финальном состоянии.
- **Сроки:** первое улучшение за 3 месяца, полная трансформация за 1 год.
- **Бюджет:** ограничен.
- **Команда:** 35 человек, но нет выделенных SRE, технических писателей и бизнес-аналитиков.
- **Инфраструктура:** нет контейнеризации, оркестрации, кэша, очередей.

Рассматривались четыре альтернативы:

### Альтернатива 1: Оставить монолит без изменений
**Плюсы:**
- Минимальные изменения, нулевой риск на этапе разработки.
- Нет затрат на новую инфраструктуру.
**Минусы:**
- Не выдержит рост нагрузки (прогноз >150 мс при 18 000 RPS).
- Единая БД – единая точка отказа, нет запаса по производительности.
- Нарушение SLA приведёт к штрафам и потере клиентов.

### Альтернатива 2: Модульный монолит (рефакторинг внутри)
**Плюсы:**
- Чёткие границы модулей, изолированные схемы данных, публичные интерфейсы.
- Сохранение ACID-транзакций.
- Быстрее, чем полный переход на микросервисы.
**Минусы:**
- Всё ещё единый рантайм – нельзя масштабировать критичные компоненты отдельно.
- Единая БД остаётся узким местом.
- Не решает проблему асинхронности и кэширования – нужны дополнительные улучшения.

### Альтернатива 3: Полный переход на микросервисы сразу
**Плюсы:**
- Максимальная гибкость, независимое масштабирование каждого сервиса.
- Собственные БД для каждого сервиса.
**Минусы:**
- Огромные затраты времени и бюджета (не уложимся в 3 месяца).
- Потеря ACID-транзакций (нужна Saga).
- Команда не готова к микросервисной культуре, нет Kubernetes.
- Высокий риск сбоев и простоев при миграции.

### Альтернатива 4: Strangler Fig Pattern (постепенное замещение)
**Плюсы:**
- Постепенное вырезание функциональности из монолита, каждый шаг обратим.
- Минимизация рисков, сохранение бизнес-непрерывности.
- Параллельная работа над улучшениями инфраструктуры (кэш, очередь, реплики).
- Готовит почву для полных микросервисов в долгосрочной перспективе.
**Минусы:**
- Усложнение операционного управления (гибридный режим).
- Требуется дисциплина в организации интерфейсов между старым и новым.
- Дополнительные накладные расходы на маршрутизацию трафика.

## Решение

Выбран **Strangler Fig Pattern**. На первом этапе (3 месяца) мы внедряем инфраструктурные улучшения (Redis, Kafka, read-реплику PostgreSQL) и выделяем **Сервер аукциона** в отдельный микросервис, оставляя остальные компоненты в монолите. В течение года последовательно выносим Рекламный сервер, Сервис выдачи, Сервис статистики и другие. На каждом этапе система остаётся работоспособной, а нагрузка переключается на новые сервисы по мере готовности.

## Последствия

**Положительные:**
- Минимальные риски для бизнеса – каждый шаг тестируется и внедряется постепенно.
- Возможность быстро улучшить производительность (кэш, асинхронность) уже в первые месяцы.
- Команда учится работать с микросервисами без шоковой терапии.
- Чёткое разделение ответственности и возможность масштабировать только нагруженные компоненты.

**Отрицательные:**
- Временное усложнение архитектуры (монолит + микросервисы).
- Необходимость поддерживать обратную совместимость и маршрутизацию между частями.
- Дополнительные затраты на мониторинг и оркестрацию гибридной системы.

**Риски:**
- Если внедрение нового сервиса затянется, старый монолит может не выдержать пиковой нагрузки. **Меры:** приоритизация критичных компонентов, жёсткий контроль сроков.
- Сетевое взаимодействие между монолитом и новыми сервисами может добавить задержку. **Меры:** использовать gRPC и держать сервисы в одном кластере, минимизировать число вызовов.
- Команда может нарушить границы при разработке новых фич. **Меры:** ввести код-ревью.


# ADR-002: Выделение сервера аукциона в качестве первого приоритета

**Дата:** 2026-09-08
**Статус:** Accepted

## Контекст

Сервер аукциона (Auction Engine) – наиболее критичный компонент по latency и нагрузке. Он обрабатывает каждый bid-запрос, применяет бизнес-правила, выполняет синхронные запросы к PostgreSQL для чтения ставок и кампаний. Именно его деградация напрямую влияет на общее время ответа и вероятность проигрыша аукционов. В текущей архитектуре он жёстко связан с другими модулями и не может масштабироваться независимо.

Архитектурные драйверы для этого решения:
- **Латентность:** необходимо снизить P95 до < 100 мс, а лучше до 80 мс.
- **Масштабируемость:** обеспечить горизонтальное масштабирование именно этого компонента под растущий RPS.
- **Устойчивость:** изолировать сбои аукциона от остальной системы.
- **Сроки:** первый релиз должен быть готов через 3 месяца.

## Решение

**Сервер аукциона выделяется в отдельный микросервис** на первом этапе (первые 3 месяца). Он будет упакован в Docker-контейнер и развёрнут в Kubernetes-кластере с горизонтальным автомасштабированием. Взаимодействие с Рекламным сервером (пока в монолите) осуществляется через gRPC. Для снижения нагрузки на БД внедряется Redis-кэш для данных кампаний и ставок. Запись результатов аукциона (победитель, цена) продолжается в PostgreSQL, но теперь только через этот сервис.

## Последствия

**Положительные:**
- Значительное снижение времени отклика за счёт кэширования и возможности масштабирования.
- Возможность независимо обновлять и улучшать логику аукциона без влияния на другие части системы.
- Появляется задел для дальнейшей декомпозиции – другие сервисы могут взаимодействовать с аукционом через чёткий API.

**Отрицательные:**
- Сетевое взаимодействие между монолитом и новым сервисом добавляет несколько миллисекунд (компенсируется кэшем).
- Необходимость поддерживать две версии логики (пока монолит ещё содержит старый код) в период миграции – требуется аккуратное отключение старого пути.
- Увеличение сложности деплоя и мониторинга (два разных компонента).

**Риски:**
- Сбой в новом сервисе может полностью остановить аукцион. **Меры:** внедрить Circuit Breaker.
- Неправильная настройка кэша (устаревшие данные) приведёт к неверным ставкам. **Меры:** использовать TTL.
- Задержка в gRPC может превысить ожидания. **Меры:** держать сервисы в одном Kubernetes-кластере, использовать локальный сетевой интерфейс, оптимизировать размер сообщений.


# ADR-003: Выбор технологии для потоковой обработки событий

**Дата:** 2026-09-08
**Статус:** Accepted

## Контекст

Сервис статистики в текущей архитектуре записывает каждый клик и показ напрямую в PostgreSQL синхронно, создавая высокую write-нагрузку и конкуренцию с транзакционными запросами. Это один из главных факторов деградации latency. Необходимо перейти к асинхронной обработке событий, чтобы разгрузить БД и обеспечить буферизацию при пиковых нагрузках.

Архитектурные драйверы:
- **Пропускная способность:** обработка миллионов событий в секунду.
- **Надёжность:** гарантия доставки (at-least-once), устойчивость к сбоям.
- **Масштабируемость:** возможность увеличивать количество потребителей.
- **Задержка:** приемлемая (несколько секунд) для аналитических целей.
- **Интеграция:** поддержка языков Python, Go, Node.js (используемых в системе).

Рассматривались две альтернативы:

### Альтернатива 1: RabbitMQ
**Плюсы:**
- Простота настройки, хорошая документация.
- Поддержка различных протоколов.
**Минусы:**
- Ограниченная пропускная способность при очень высоких нагрузках (миллионы событий/сек).
- Сложнее масштабировать горизонтально (требуется кластеризация с определёнными ограничениями).

### Альтернатива 2: Apache Kafka
**Плюсы:**
- Высокая пропускная способность (миллионы сообщений/сек).
- Гарантированная доставка с возможностью настройки durability.
- Горизонтальное масштабирование через партиционирование.
- Широкая поддержка клиентов для разных языков.
- Возможность долгого хранения событий для повторного воспроизведения.
**Минусы:**
- Сложность настройки и администрирования.
- Небольшая задержка (порядка миллисекунд) – допустима для аналитики.

## Решение

Использовать **Apache Kafka** как центральный брокер событий. Сервис выдачи будет публиковать события показов и кликов в топик. Сервис статистики (потребитель) будет читать из топика и записывать агрегированные данные в ClickHouse. Также этот же топик может использоваться для финансовых событий и других нужд. Для обеспечения отказоустойчивости настроим репликацию и минимум 3 брокера. На первом этапе развернём Kafka в том же Kubernetes-кластере.

## Последствия

**Положительные:**
- PostgreSQL освобождается от write-нагрузки, снижается конкуренция.
- Возможность буферизировать пиковые нагрузки – события не теряются, даже если потребитель временно недоступен.
- Появляется архитектурная основа для других асинхронных сценариев (например, уведомления, финансовая сверка).
- Возможность масштабировать количество потребителей независимо.

**Отрицательные:**
- Добавление нового компонента в инфраструктуру (требует администрирования).
- Небольшая задержка между событием и его отражением в отчётах – допустимо.
- Необходимость обучения команды работе с Kafka.
- Дополнительные затраты на хранение (хотя можно настроить политику очистки).

**Риски:**
- Неправильная конфигурация репликации может привести к потере данных при сбое брокера. **Меры:** использовать минимум 3 брокера, настроить replication factor = 3.
- Потребитель может не успевать обрабатывать поток, если неправильно настроены партиции. **Меры:** увеличить число партиций, использовать группы потребителей для параллельной обработки.
- При сбое сети между сервисами и Kafka может возникнуть задержка публикации. **Меры:** настроить таймауты и ретраи с экспоненциальной задержкой.
- Отсутствие мониторинга Kafka приведёт к невидимым проблемам. **Меры:** внедрить мониторинг через Prometheus и Grafana, настроить алерты на падение брокеров и переполнение логов.
