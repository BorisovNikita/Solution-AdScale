# Целевая архитектура (TO-BE)

## Выбор архитектурного стиля

### Сравнение подходов

| Критерий | Монолит (текущий) | Модульный монолит | Strangler Fig Pattern | Постепенная декомпозиция (без явного паттерна) |
|----------|---------------------|-------------------|------------------------|------------------------------------------------|
| **Скорость реализации** | - | Высокая (рефакторинг внутри) | Средняя (параллельная разработка) | Низкая (долгий поэтапный перевод) |
| **Риск потерь для бизнеса** | Низкий (не меняем) | Средний (рефакторинг может сломать функциональность) | Низкий (постепенное замещение с возможностью переключения функциональности) | Высокий (долгий период гибрида без чёткой стратегии) |
| **Масштабируемость** | Отсутствует | Ограниченная | Высокая (достаточная) (выделенные сервисы масштабируются отдельно) | Высокая (в итоге микросервисы) |
| **Сложность управления** | Низкая | Средняя (модули, но единое исполнение) | Высокая (сетевое взаимодействие, маршрутизация, взаимодействие между компонентами) | Высокая (аналогично тому, что слева, накладные расходы) |
| **Возможность инкрементальных улучшений** | Нет | Да (внутренние модули) | Да (постепенное вырезание) | Да, но менее структурированно |
| **Подходит для долгосрочного роста** | Нет | Частично (до определённого предела) | Да (потенциально микросервисная) | Да (но требует жёсткого плана) |

**Выбранный подход: Strangler Fig Pattern**

**Обоснование:**
- **Почему не оставить монолит?** - монолит не позволяет масштабировать компоненты независимо и не выдерживает рост нагрузки; единая БД и отсутствие асинхронности создают непреодолимые узкие места, невозможно предоставить требуемый функционал.
- **Почему не переписывать сразу на микросервисы?** - это слишком рискованно, дорого и длительно; бизнес-непрерывность нарушится; команда не готова к полной смене парадигмы; нет таких ресурсов ни человеческих ни финансовых.
- **Почему Strangler Fig лучше модульного монолита?** - модульный монолит улучшает организацию кода, но не даёт возможности масштабировать части по отдельности и не решает проблему единой БД. Strangler Fig позволяет постепенно выносить критические компоненты в отдельные сервисы с собственными БД, что даёт реальный прирост производительности и устойчивости, сохраняя при этом работоспособность системы на каждом этапе, также позволит в кратчайшие сроки вырезать критичные компоненты, в работоспособность которых упираются основные бизнес ограничения.

## Целевое состояние (через 1 год)

### Сервисы и их границы (русские названия)

1. **API Gateway** - единая точка входа для всех внешних запросов (рекламодатели, DSP, пользователи). Маршрутизация, аутентификация, rate limiting.
2. **Рекламный сервер** - принимает bid request, определяет пользователя, подбирает кандидатов (бывший Ad Server).
3. **Сервер аукциона** - вычисляет ставки и определяет победителя (бывший Auction Engine), критичен по latency, использует кэш Redis.
4. **Сервис выдачи** - генерирует разметку баннера и возвращает ответ.
5. **Сервис статистики** - асинхронно обрабатывает события показов/кликов из Kafka, записывает в выделенную БД (ClickHouse).
6. **Сервис аналитики** - строит отчёты на основе данных из ClickHouse, не влияет на OLTP, существует по сути отдельно от него, не пересекается.
7. **Финансовый сервис** - управляет балансами, транзакциями, работает с отдельной БД (шардированной).
8. **Рекламный кабинет** - веб-интерфейс, взаимодействует с API Gateway.

### Инфраструктурные компоненты
- **Redis** - распределённый кэш для данных аукциона (кампании, ставки, правила таргетинга).
- **Kafka** - брокер событий для потоковой обработки кликов/показов, а также для межсервисного взаимодействия (асинхронные команды).
- **API Gateway** - на базе Envoy Proxy.
- **Базы данных**:
  - **PostgreSQL (основная)** - для транзакционных данных (кампании, финансовые операции). Шардирование может быть использовано.
  - **PostgreSQL read-replica** - для отчётности и аналитики на первом этапе, затем заменяется на ClickHouse.
  - **ClickHouse** - для хранения событий и быстрой аналитики.
- **Контейнеризация и оркестрация** - Docker + Kubernetes, HPA по RPS/CPU.
- **Мониторинг** - Prometheus, Grafana, Jaeger.

### Взаимодействие
- **Синхронные** (gRPC/HTTP) - для критических путей: Рекламный сервер -> Сервер аукциона, Сервер аукциона -> Redis (внутренний). Внешние запросы через API Gateway.
- **Асинхронные** (Kafka) - для событий: Сервис выдачи -> Kafka -> Сервис статистики, а также для уведомлений (пуши) о финансовых транзакциях.

## Этапы миграции (дорожная карта)
1. **Первые 3 месяца**: внедрение Redis, Kafka, read-replica; выделение Сервера аукциона в отдельный контейнер (первый микросервис).
2. **6 месяцев (условный этап, для приоритезации переезда на микросервисы)**: выделение Рекламного сервера и Сервиса выдачи; переход на асинхронную статистику.
3. **12 месяцев**: полная декомпозиция, мультирегиональность, SLA 99.9%.
